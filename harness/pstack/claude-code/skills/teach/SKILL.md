# 教える（Teach）

In Claude Code, read [the Claude Code adapter](../../docs/harness/claude-code.md) once per session before you follow this skill. It maps the Cursor names in pstack skills to Claude Code.

**あるものが何で、どう動き、なぜそう作られているかを、相手のペースに合わせ、1 つの平易な説明として伝える。目的は相手が理解することであり、何かを変更することではない。**

teach は `how` と `why` の上に成り立つ。まず、その作業が何で、何に関係するかをつかみ、それから仕組みについては `how` を、理由については `why` を実行する。どちらも実際のスキルの呼び出しであり、それぞれが自分で調べる。その結果を 1 つの平易な説明にまとめ、相手にとって大事なことから話し、求められたらさらに詳しく説明する。教えるために自由に言い換えてよいが、例外が 1 つある。`why` の確信度を表す言い回しはそのまま残す（その留保は文体ではなく、調査結果である）。

1. 相手に最終的に理解してもらうべきことを、少数に絞って決める。相手がなぜ尋ねているのか（これから変更する、レビューする、デバッグする、初めて触れる）と、すでに何を知っているかから選ぶ。どちらも会話から読み取り、相手に質問して聞き出さない。明らかにすでに知っていることは飛ばす。詳しさは、相手の問いがある箇所に割く。
2. 仕事は `how` と `why` に任せ、自分でやり直さない。全体をつかむために自分でもコードを読み、それから仕組みについては `how` を、理由については `why` を実行する。両方を並列に実行し、結果を組み合わせる。規模は問いに合わせる。サブシステムなら両方を実行し、小さな変更なら片方で足りるかもしれない。
3. 平易な定義から始める。対象に名前を与え、それが一般に何であるかを、シニアエンジニアが口頭で言うように説明する。一般的な呼び名があれば、それも添える。それから目の前のケースに結びつけ（"in X, we use this to ..."（X では、これを使って……している））、そこから積み上げる（どう動くか、より深い理由、エッジケース）。各部分について、相手が腑に落ちるように考え方を説明する（それが解決する問題と、実際にどう動くか）。相手がその操作をするときに何が起きるか（長いチャットを開く、上にスクロールする）を順に追うのが理解につながるなら、そうする。関数や定数を列挙するのはリファレンスであって、教えることではない。枠付けのラベル（"the one idea to hold onto"（押さえておくべき 1 つの考え）、"the thing to walk away with"（持ち帰ってほしいこと）、"the key insight"（重要な洞察）、"at its core"（突き詰めると）、"TL;DR"（要約））を出力しない。まず最小限で完結した答えを、密な段落ではなく 1〜2 文で示し、そこで止める。求められたら説明を重ねる。決して長大な文章の塊にしない。
4. 講義や演技ではなく、会話にする。さらに詳しく説明するか先に進むかを提案し、相手の意向に従う。クイズを出さない。間合いを演出しない。"Pause"（一時停止）と出力しない。相手に復唱させない。"the sentence to nail"（押さえるべき一文）と予告しない。ある部分を重要だ、難しいと前置きしない（"here is the part worth slowing down on"（ここはじっくり見る価値がある）、"this is the tricky part"（ここが難しいところだ）、"here is where it gets interesting"（ここからが面白い））。そのまま言う。間を置きたくなったら、そこで止めて相手の返答を待つ。人間が同席しない 1 回きりの実行なら、すっきりと伝え、さらに詳しく説明する提案は最後に置く。
5. 言葉で語るだけでなく見せる。図は 1 枚ずつ積み上げて全体像を作る。差分、コード、デバッガーを開くのが最も速く伝わる方法なら、それを開く。言葉より絵のほうが速く伝わるなら、図を描く。動く部品が 3 つ以上あるものは、全部を一度に入れた図を 1 枚描くことはしない。代わりに短い連作を描き、各図で前の図を描き直して部品を 1 つだけ足し、システムが組み上がっていく様子を読み手が見られるようにする。全部を一度に入れた 1 枚の図は、特に最後に取っておいたものは、リファレンスであって教えることではない。具体的には、A から B、B から C への流れを教えるなら、3 回描く。最初は A から B。次に描き直して C を足す。次に描き直して、戻りの辺か次の部品を足す。媒体は考えに合わせ、両方が役立つなら両方を使う。mermaid の図は、ラベルで意味が伝わる流れや構造に向いている。レイアウト、重なり、スクロール位置、変更前と変更後のように考えが空間的なものなら、画像生成ツールを使い、短いラベルをいくつか付けて、ホワイトボードにマーカーで描いたような絵にする。画像モデルは長い文字列を崩してしまうからである。その絵は実際に生成し、言葉で描写するだけで済ませない。積み上げの規則は、生成した画像にも当てはまる。単純な要点 1 つなら、図は要らない。

どの応答も **unslop** スキルを通し、同僚に説明するときのような平易な話し言葉の英語で書く。簡潔にするが、素っ気なくはしない。埋め草と予防線は削り、腑に落ちるための部分は残す。比喩、枠付け、これから話すことの予告ではなく、具体的な仕組みを述べる。目指す密度は次のとおりである: "Virtualization runs in two parts, one for rendering and one for loading from disk. When an item scrolls out past the buffer, both its DOM node and its in-memory data are evicted."（仮想化は 2 つの部分で動く。1 つは描画、もう 1 つはディスクからの読み込みである。項目がスクロールしてバッファの外に出ると、その DOM ノードとメモリ上のデータの両方が追い出される。）すべて小文字ではなく、通常の sentence case で書く。em ダッシュを使わない。カンマよりピリオドを選ぶ。1 文のカンマは 1〜2 個までにする。節が積み重なるなら、別々の文に分ける。1 つの概念には 1 つの名前を与え、それを使い続ける。鏡写しの文（"A without B, or B without A"（B のない A、または A のない B））や、きれいにまとめる締めの文（"the rest follows"（あとは自然に決まる）、"it all falls out"（すべてがそこから導かれる））を避ける。これらの手順の言葉は自分への指示であって、出力するラベルではない。その構成を見出しや決まり文句として繰り返さない。

**返答:** 説明そのもの。決して、何をしたか・何を渡したかの報告にしない。要点を先頭に置き、次にそれが何で、どう動き、なぜそうなのかの平易な説明を書き、`how` や `why` で追う価値のある論点を添える。
