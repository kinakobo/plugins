### マージまでの自動実行（Autopilot-full）

**自分が責任を持つのは判定であり、決して PR ではない。各 PR は、1 つのオーナーが構築からマージまで担当する。コードを書いていない自分の swarm が、マージされるコードを証明するまで、何もマージしない。**

判定が対象とするのは 1 つのパッチであり、CI の成功が対象とするのは 1 つの head である。手順 4 では、完全な swarm を 1 回実行し、大きな変更があったときだけもう一度実行する。`playbooks/shipping.md` の patch-id の規則によってレーンの結果を引き継げることはあるが、新しい head にはそれぞれ CI の成功が必要である。

1. **オペレーターのゲートを最優先にする。** 与えられた権限が及ぶのはキューの項目だけなので、オペレーターが自分のものだと名指しした項目と、キューの外の PR は、マージ可能（merge-ready）の状態で止める。計画を述べてほしいという依頼は、実行の許可ではない。
2. **PR ごとにオーナーを 1 つ起動し、その作業を、交代したエージェントが見つけられる場所に残す。** フォージはプログラム全体で 1 回だけ決める。既定は GitHub CLI（`gh`）である。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の操作にはすべて `origin pr` を使う。そうでなければ `gh` を使い続け、フォールバックしたことを記録する。決して Graphite（`gt`）を必須にしない。各オーナーは Cursor の cloud agent で、構築し、`playbooks/opening-a-pr.md` に従って PR を開き、実物の成果物で変更を証明し、`playbooks/babysit.md` に従って CI が通るまで見守り、手順 4 と 5 で許可が出たらマージする。そのプレイブックがリベースを報告するよう指示している箇所では、オーナーが自分のブランチをリベースし、`git push --force-with-lease` で公開する。

   作業と並行して CI とボットが動くよう、PR は早めに開く。コードが完成（code-ready）になるのは、slop の除去（`cursor-team-kit` プラグインの `deslop` スキル（`/deslop`））と `/no-comments` の処理を終えたあとだけである。こうすれば、完全な swarm は完成したコードに対して実行される。そのあと現在の trunk にリベースし、自己証明の前に code-ready の head を報告する。こうすれば、検証はパッチがマージされるベースの上で実行される。以降の head はすべて報告し、自己証明、CI、見守りが終わったら merge-ready を報告する。修正のラウンドは、trunk がコンフリクトを起こすか、CI を壊すか、同じファイルへの既知の並行変更を取り込まない限り、そのベースのまま行う。リベースのたびに CI がやり直しになるからである。code-ready の push の前と、検証役が必要になる以降の push の前には、変更したパスに対するリポジトリのチェックを、コミット済みの head で実行する。

   VM は落ちるものと考える。開始してすぐに push し、**show-me-your-work** スキルに従って、ルートのエージェントのストア（パスはシステムプロンプトにある）で決定の記録（decision trail）を始める。そのあとは、終わった単位を push してから次の単位を始める。サブエージェントを起動した者は、そのストアに、サブエージェントの ID、状態、同じ種類の過去の実行から見積もった停滞とみなすまでの実行時間（stuck-after runtime）を記録する。こうすれば、親が落ちてもルートがそのサブエージェントを調べられる。force-push は自分のブランチにだけ行い、`--force-with-lease` を、自分が最後に push したか引き継いだ SHA に固定する。自分がしていない push を見つけたら、止まってルートに報告する。
3. **オーナーは trunk から分岐させて並列に動かし、決して積み重ねない。** 各 PR を単独でマージできるようにするためである。
4. **swarm での検証は 1 回にする。** 完全な swarm は、code-ready の head で 1 回だけ実行する。もう一度完全な swarm を実行するのは、新しい振る舞い、設計のやり直し、大きな新しい差分があるときだけである。リベース、マージのコンフリクトの解消、小さな修正には、新しい head で検証役を 1 つだけ付け、文言だけの変更には付けない。**swarm** スキルに従って、code-ready の SHA で独立した検証役をファンアウトする。検証役はゲートを再実行し、要となる振る舞いを、その操作用のスキル（`cursor-team-kit` の `control-ui` や `control-cli` など）か名前を挙げたドライバーを通じて、実際のインターフェースの上で動かして証明し、差分を監査する。実際に動かすレーンがなければ、また merge-ready の報告の裏付け（receipts）を監査する前は、判定はクリーンにならない。どのレーンも、自分で確かめていない主張は信用しないからである。

   PR をブロックするのは、示せる問題があるとき、つまり head で失敗した実行か、その PR が誤りにしたドキュメントの行があるときだけである。PR のベース（trunk でも、スタックで下にある PR でも）にすでにある問題は、その PR がそれを写したか、新たにそこへ到達するようにしたのでなければ、ブロックの理由にならない。ブロックするのは、ユーザーが遭遇するバグ、失敗したゲート、リリースされる誤ったドキュメントだけであり、それ以外はすべて後続の作業に回す。
5. **オーナーがマージするのは、自分が検証し、マージ先の trunk でテストしたものだけである。** CI の成功だけでマージが許されることは決してない。swarm のレーンが始まったら、マージの準備として、現在の trunk にリベースし、新しい head を報告し、CI が通るのを待つ。

   マージの直前に trunk を fetch し、その変更がパッチに影響しうるかを考える。trunk が動くたびにリベースしていては終わらないからである。マージされるコードが一度もテストされていないとき、たとえばコンフリクトがあるとき、両側が変えたファイルがあるとき、PR に対してどのチェックが走るかを変える変更があるときは、リベースして CI を待つ。両側が変えた lockfile は、マージ結果で frozen install が通り、PR が変えたパッケージがそこで head と同じように解決されるなら、リベースは要らない。その install が、マージされる lockfile をテストしているからである。install が失敗するなら、リベースで直さなければならない。trunk がパッチの呼び出し元か、パッチが依存するもの（呼び出すコードや依存のバージョンなど）を変えたときは、マージ結果でパッチのチェックを実行し、通ったらマージする。それ以外はそのままマージする。マージの準備のあとに trunk のせいで 3 回目のリベースが必要になりそうなら、止めてルートに報告する。衝突する作業の順序はルートが決める。
6. **ルートの層を動かす。** ゲートを緩めるもの（予算の引き上げや許可リストへの追加など）には、検証役の証明と、そのあとの自分の新たな副署（countersign）が必要である。CI を通したがっているのはオーナー自身だからである。承認まで含む権限が与えられているときは、その副署が承認になり、オーナーはその記録に、レーンが確かめられるよう自分の副署への参照を残す。チェックの無効化や soft-fail 化は、必ず取り消す。そうしたチェックは、どのケースも守らなくなるからである。フォージが強制する承認は、決して与えたり回避したりしない。どの副署もそれを代わりにできないからである。

   オペレーターの許可が出たら、委任した作業が残らなくなるまで監査するよう `/loop 1h` を設定する。長い実行はずれていき、エージェントは黙って止まるからである。各回（tick）では、trunk からこのプレイブックを読み直し、ずれ（報告されていない head や記録されていないエージェントなど）を、そのオーナーに記録させて直す。ずれは記録の欠けであって、停滞ではないからである。末端のレーンまで、すべてのエージェントを調べ、それぞれを副作用で判断する。状態の文言や要約は、停滞した子を隠すことがあるからである。エラーを出したエージェント、ターンを始められないエージェント、停滞とみなすまでの実行時間を過ぎても何も新しいものを出していないエージェントは、停滞している。最初の回までに push もせず記録の行も書いていないオーナーも同じである。自分かオペレーターを待っているエージェントは停滞していないので、それに答える。停滞したエージェントは、その停止が完了するのを待たずに、すぐに置き換える。オペレーターにとって何かを変えた回は、**ketchup** スキルに従ってオペレーターに状況を伝えて終える。何も変えなかった回は何も言わない。
7. **オペレーターが止めたら、すぐに手を止める。** 保留は、書き込みを一切しないという指示としてすべてのオーナーに伝わる。各オーナーは現状を報告し、オペレーターが解除するまで依頼文を保持する。

**返答。** **ketchup** スキルに従ってオペレーターに状況を伝える。各 PR の状態と判定、マージしたもの、副署とその理由、未解決のオペレーターのゲート、保留した後続の作業を含め、各 PR と記録へのリンクを付ける。
