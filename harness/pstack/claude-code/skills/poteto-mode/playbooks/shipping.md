### リリース（Shipping）

**マージされるものは自分の責任である。各 PR を独立に検証し、根元から続く検証済みの連なりだけをマージし、そのあとはスタックに手を出さない。**

1. **フォージを決め、各 PR をマージの前に独立に検証する。** 既定は GitHub CLI（`gh`）である。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、PR の操作にはすべて `origin pr` を使う。そうでなければ `gh` を使い続け、フォールバックしたことを記録する。決して Graphite（`gt`）を必須にしない。PR ごとに 1 つの検証役（それぞれ Cursor の cloud agent）が、対応する操作用のスキル（`cursor-team-kit` の `control-ui` や `control-cli` など）を使い、親と head を比べながらユーザーと同じように変更を動かし、その PR に `PASS`、`PASS+NOTES`、`FAIL` のいずれかを投稿する。判定として数えるのは、コードを書いていないエージェントの判定だけである。作者は、自分が作ろうとしたものを確かめてしまうからである。CI の成功や、ボットの承認レビューは判定ではない。どちらもユーザーのように変更を動かさないからである。
2. **最下部から途切れずに続く、検証済みの連なり（run）だけをマージする。** マージされていない最も下の PR から上へたどり、`PASS` も `PASS+NOTES` もない最初の PR で止まる。それより下の PR が連なりであり、そのうち最も上の PR が上限（ceiling）である。未検証の PR の上にある検証済みの PR は待つ。下のコードがなければマージできないからである。ブランチがそのコードを含まず、必要ともしない PR は、trunk の上に移して単独でマージしてよい。ただし、先に新しい判定が要る。古い判定はそのコードが下にある状態で実行されたもので、trunk にはそのコードがないからである。
3. **判定がまだそのコードに当てはまるかを確かめ直す。** 判定が対象とするのはパッチであり、連鎖したリベースは、どのチェックも落とさずに、その上のすべての PR を新しい SHA に移す。古い判定を信用する前に、判定時の SHA と現在の head とで `git patch-id` を比べる。パッチの違いがテスト、ドキュメント、lint の設定だけなら、レーンが実行したものが両方の SHA でノイズを除いて同じにビルドされる場合に限り、そのレーンの結果は有効なままである。ノイズとは、判定時の SHA を 2 回ビルドしたときにも現れる違いか、埋め込まれたコミットの SHA である。読み手がその判断を確かめられるよう、ノイズの種類ごとにそのファイルを報告する。変更そのものには、改めてチェックとレビューを行う。古い判定はその変更を見ていないからである。ビルドの出力がないレーン（開発サーバーなど）ではこれを示せないので、再実行する。ほかにずれたものも、すべて検証し直す。
4. **下から上へ、1 つずつマージする。** 必ず、連なりのうちマージされていない最も下の PR を、`origin pr merge <pr>` か `gh pr merge <pr> --squash` でマージする。Origin では、オプションなしのコマンドは、指定した PR より下の PR もすべてマージする。GitHub では、ベースがまだ親のブランチである PR は、trunk ではなくそのブランチにマージされる。結果は PR を読み直して確かめる（`origin pr view <pr>` か `gh pr view <pr> --json state,mergedAt,baseRefName`）。マージキューが PR をキューに入れただけでもマージのコマンドは成功を報告することがあり、自動マージを依頼しただけではマージではないからである。マージされた PR は、状態が merged で、ベースが親のブランチではなく trunk になっている。`--auto`（Origin の merge-when-ready か GitHub の自動マージ）は、判定が現在の head を対象としている PR にだけ設定する。`--auto` は、準備ができた head を、それが何であれマージするからである。マージが完了したら、マージされたブランチをベースにしていた PR のベースを trunk に変え（`origin pr edit <pr> --base <trunk>` か `gh pr edit <pr> --base <trunk>`）、そのパッチをマージ結果の上に移して、`--force-with-lease` で push する。判定が対象とするのはパッチであってコミットではないので、判定が有効なままかどうかは手順 3 の patch-id の規則で決まる。チェックが通り、判定が有効なままなら、その PR をマージする。
5. **マージしているあいだは、スタックに手を出さない。** ブランチやベースへの変更は、手順 4 で次の PR を移すことだけにする。マージは、判定があるかどうかにかかわらず、その時点でブランチとベースにあるものをマージするからである。GitHub では、`/loop` のもとで `scripts/watch-pr/watch-pr --queued-stack` を使い、上限の PR で `COMPLETE` が報告されるまで連なりを見守る。`--stack-prs` には連なりの PR 番号を下から上の順に渡し、watcher を再起動するたびに同じ一覧を渡す。Origin では、`origin pr checks <pr> --watch` が戻るたびに `origin pr view <pr> --checks` で現在の PR を読み直し、上限の PR が merged になるまで続ける。親がマージされたときにベースが trunk に移るのは想定どおりであり、直すべき損傷ではない。マージが止まったら、何かを変える前に原因を突き止める。
6. **上限で止まる。** 連なりを延ばすには新しい判定が要るので、それは手順 1 からの新しい一巡になる。

**返答。** 検証済みの連なりとその上限、各 PR の判定とそれを出したエージェント、マージしたものとそれをどう確かめたか、次の切れ目を埋めるのに何が要るか。
