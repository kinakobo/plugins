# コメントを残さない（No comments）

In Claude Code, read [the Claude Code adapter](../../docs/harness/claude-code.md) once per session before you follow this skill. It maps the Cursor names in pstack skills to Claude Code.

Comment Sicko を起動する。採用した指摘に対応する。

Comment Sicko の、先入観のない視点に判断を委ねる。

## 範囲（Scope）

呼び出し元が指定したファイルか diff を使う。指定がなければ、ベースブランチ（既定は `main`）に対する現在の diff を、作業ツリーを含めて使う。

## 手順（Steps）

1. `subagent_type: "comment-sicko"` を付けて `Task` を起動する。範囲を渡す。各サブエージェントの推論のレベルは、**poteto-mode** スキルのサブエージェント（Subagents）の節に従って、作業に合わせて選ぶ。comment-sicko のルールを言い直さない。
2. 報告と diff を調べる。アプリケーションのコードへの編集、範囲外への逸脱、例外で保護されたものの削除、理由を誤って述べた `MUST KILL`、意図して残したコードを有罪扱いする指摘は却下する。自分たちのコードの意外な点についての作り直し（reshape）の指摘は、対応が必要なものとして扱い続ける。そうしたコメントは復元しない。残す判定（keep）が通るのは、そのコメントが自分たちには変えられないものについてのものだという証明があるときだけである。範囲内で見落とされた lint や TypeScript の抑制を監査する。正しさや安全性に関わる抑制は、対応が必要な `MUST KILL` のままとする。削除を復元するのは、該当する例外が正確に当てはまり、範囲内での証明があるときだけである。根拠の薄い `IMPORTANT` や `do not remove` について、削除（kill）や残す（keep）の判定を受け入れる前に、そのシンボルをたどるか、それに対して `/why` を実行する。削除の判定があいまいなら、復元しない。残す判定が反証されたか、依然としてあいまいなら、そのコメントを削除する。却下した報告は 1 回に限り、変更を戻し、失敗の内容を明示して再実行させる。2 回目の報告も却下したら、未解決として報告し、`/no-comments` を失敗で終える。
3. 自明な採用済みの指摘は、使われない経路を削除する、パラメータを落とす、本来の API を使う、といった方法で直接直す。形の設計が必要な修正があれば、採用した指摘の全体と周辺のコードを対象に `/architect` を 1 回実行する。素描の段階で止める。architect は形を決める。手順 4 が実装する。
4. 範囲内で、根本原因に対する最小の修正を実装する。指摘された回避策はすべて取り除く。根本原因が範囲外にあるなら、範囲内の最小の修正を入れ、残りは未解決として報告する。**principle-fix-root-causes** スキルと **principle-redesign-from-first-principles** スキルは、意図を示すだけである。どちらも、作業範囲の境界（fence）を広げることも、その外にある事例を直すことも認めない。症状に対するガードを決して後付けしない。
5. 制約コメントとは、`do not remove`、`do not change wording`、`talk to X before changing` のように書かれたコメントである。自分たちには変えられないものについての、残す判定のコメントはそのままにする。範囲内で最も安価な型、実行時のチェック、テスト、CI の lint を提案する。対話の場合は承認を待つ。無人実行と eval では、呼び出し元の事前承認が必要である。承認されたら、制約を構造に埋め込んでからコメントを削除する。承認されなければ、コメントを削除し、制約を未解決として報告し、範囲外の作業を素描する。
6. 削除した数、復元したコメント、再実行、architect の素描、修正、埋め込みの提案、実施した埋め込み、強制されていない制約、その他の未解決の作業を報告する。
