# 形式検証スキルを保守する（Maintain a formal verification skill）

In Claude Code, read [the Claude Code adapter](../../docs/harness/claude-code.md) once per session before you follow this skill. It maps the Cursor names in pstack skills to Claude Code.

形式的なチェックが証明するのは、それが記述するものの性質である。コードが変わって検証が変わらないと、チェックは、もう存在しないコードを記述したまま通り続けることがある。この通過は証明のように見えるので、危険である。このスキルは、`/create-formal-verification-skill` が生成した検証スキル、または名前を挙げたコードに対してモデル検査器、証明器、コードレベルの検証器を動かす任意のプロジェクトローカルのスキルを保守するループである。プロジェクトローカルのスキルは、エージェントがそのスキルを使いながら加える変更を扱う。このスキルは、それを通らなかった変更を扱う。マージ、スキルを使わずに加えた編集、多くのコミットにわたって積み重なったずれ（drift）である。

## 結果（Outcomes）

チェックごとに結果を 1 つ決め、どれかを明言する。

- **in sync**（同期済み）: 最後の同期以降の変更のどれも、チェックが記述するものを変えておらず、チェックは通る。
- **updated**（更新済み）: コードが変わり、検証は今では新しいコードを記述しており、チェックは通る。
- **bug**（バグ）: 検証は現在のコードを記述しており、コードが性質を破っている。これはコードについての発見であり、ずれではない。
- **blocked**（行き詰まり）: チェックをコードに合わせ直せなかったか、実行できなかった。理由を正確に述べる。

1 つのチェックが updated と bug の両方になることもある。更新によって検証がふたたびコードを記述するようになり、そのうえで性質がそのコードで失敗する場合である。

## 編集の範囲（Edit scope）

編集するのは検証だけにする。モデル、ハーネス、性質のファイル、検証スキルそのものである。ユーザーに頼まれない限り、実行中に製品のコードは決して編集しない。現在のコードで性質が失敗したら、通すために性質やモデルを弱めない。失敗を報告する。

## 点検の手順（Pass）

1. **チェックを見つける。** 検証スキルには決まった名前がないので、何をするかで探す。名前を挙げたコードに対して、モデル検査器、証明器、またはほかの検証器を動かすプロジェクトのスキルである。見つけたものを 1 つずつ、またはユーザーが挙げたものを読む。チェックごとに、性質、対象のコード、上限と仮定、実行するコマンド、コードを記述していると最後に確認されたコミットを集める。検証スキルがなければ、止まって `/create-formal-verification-skill` を案内する。スキルが同期コミットを記録していなければ、検証のファイルを最後に変えたコミットを使い、そうしたことを述べる。

2. **そのまま実行する。** 何かを変える前に各チェックを一度実行し、結果を記録する。ここで通っても、コードが正しいことはわからない。わかるのは、古い記述がまだ成り立つことである。ここでの失敗は、ずれのこともバグのこともある。どちらかは手順 5 まで決めない。

3. **対象のコードへの変更をすべて読む。** 対象のファイルについて、同期コミットから現在のコミットまでの差分を取り、各コミットメッセージを読む。移動したコードも探す。名前が変わった、分割された、または別のファイルに移った対象の関数は、今も対象のコードである。チェックが守る状態に触れる新しいコード（同じフィールドに書き込む新しい関数など）も探す。変更ごとに、次のどれに当たるかを決める。
   - **影響なし。** 変更が、検証の記述するものを何も変えない。整形、コメント、検証の対象外のコードの経路などである。これはコミットメッセージではなく、モデルやハーネスに照らして確かめる。
   - **検証がもうコードを記述していない。** 1 つの不可分な動作だったステップが 2 つになった、分岐が足されたか消された、チェックが移動した、新しい経路が守られている状態に届くようになった、値の範囲が変わった、などである。モデルかハーネスを変えなければならない。
   - **約束が意図的に変わった。** 変更がコードの約束を変えており、それが意図されたものであることを変更の中の証拠が示している。証拠とは、doc コメント、テスト、changelog、コミットメッセージである。性質を変えなければならず、その証拠を必ず引用する。
   - **約束が破られているかもしれない。** コードは変わったが、約束が変わったことを示す証拠はない。このあとに起きる失敗は、バグの候補として扱う。

4. **結果からではなく、コードから更新する。** 変わった部分がそれぞれふたたびレビュアーの開けるコードを指すように、モデルかハーネスを変え、コードの 1 つの不可分なステップは検証でも 1 つのステップのままにする。更新は再実行の前にコードから書き、チェックが通るかどうかで形を決めない。性質を変えるのは、意図的に変わった約束についてだけにする。古い文言、新しい文言、証拠を書き留める。変更によって上限が誤りにならない限り、上限は変えない。上限を下げなければならないなら、報告でそう述べる。

5. **再実行し、結果を 1 つずつ判定する。**
   - **通った場合:** 失敗する能力を失った記述の上で、チェックが通っているおそれがある。性質が防ぐやり方で新しいコードを壊し（新しいチェックを取り除く、新しいステップの順序を入れ替えるなど）、チェックがそれを捕まえることを確かめる。そのあと、壊した変更を捨てる。
   - **失敗した場合:** 反例を、実際のコードに対して 1 ステップずつ再現する。コードで起こりえないステップがあれば、検証が誤っている。検証を直し、何が誤っていたかを述べる。どのステップも起こりうるなら、それはバグである。それを持ち込んだコミットを挙げ、反例をコード自身の言葉でステップの列として伝え、害を 1 文で述べる。実際のコードに対する安価なテストや再現手順でバグを示せるなら、証拠として報告に加える。それを製品のコードにはコミットしない。

6. **検証スキルを更新する。** 各チェックの対象のコード、コマンド、上限、仮定、同期コミットを更新する。同期コミットは、確かめたコミットに設定する。blocked のチェックでは同期コミットを動かさず、報告でそう述べる。そのあと、次のエージェントがするとおりに検証スキルに一度従い、その手順がまだ動くことを確かめる。

## 報告（Report）

チェックごとに、次をユーザーに伝える。

- 結果と、読んだコミット。
- 検証の何をなぜ変えたか。変更ごとに短い理由を添える。コードの形が変わったのか、約束が意図的に変わったのか（証拠を添える）。
- 再実行の結果と、更新したチェックがまだ失敗できることを示すのに使った壊し方。
- 各バグを平易な言葉で。コードの言葉で書いたステップとしての反例、害、それを持ち込んだコミット。
- 検証がまだ対象にしていないもの。対象にすべきなのにしていない新しいコードも含める。

どの失敗が検証のずれで、どの失敗がコードのバグだったかをはっきり述べる。更新する前は通り、更新したあとで失敗するチェックについては、以前の通過は古くなった記述の上でのものだったと述べる。

検証の更新は、製品の修正とは分けて、独立した変更にする。
