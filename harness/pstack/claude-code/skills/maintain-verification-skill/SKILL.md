# 検証スキルを保守する（Maintain a verification skill）

In Claude Code, read [the Claude Code adapter](../../docs/harness/claude-code.md) once per session before you follow this skill. It maps the Cursor names in pstack skills to Claude Code.

機能マップは、アプリが変わった瞬間から古くなり始める。このスキルは、`/create-verification-skill` が生成したスキル（または機能マップを持つ任意のプロジェクトローカルの検証スキル）を保守するループである。厳密さの単位は機能であり、文の 1 つ 1 つではない。すべての機能ファイルをソースから網羅し、すべての機能をライブで動かすが、箇条書きの項目を 1 つずつターミナルで実行することまではしない。

## 結果（Outcomes）

次のうち 1 つを選び、どれかを明言する。

- **clean**（問題なし）: すべての機能を、ソースとライブの両方で網羅した。出す価値のある変更はない。ブランチも PR も作らない。
- **changed**（変更あり）: 証明済みの、ドキュメント、ハーネス、マップの修正を 1 つの PR で出す。
- **blocked**（行き詰まり）: 網羅を終えられなかったか、証明した修正を安全に出せなかった。何に阻まれたのかを正確に述べる。

## 編集の範囲（Edit scope）

編集するのは、検証スキル自身のディレクトリ（その SKILL.md、features/、スキルが持つハーネスのスクリプト）だけにする。実行中に製品のコードは決して編集しない。マップに書いてあるのにアプリがもうしない振る舞いは、ドキュメントのずれ（drift。マップを直す）か、製品の退行（報告する。ドキュメントで取り繕わない）のどちらかである。

## 点検の手順（Pass）

0. **対象を見つける。** 保守する検証スキルを探す。本文に起動と操作の節と機能マップを持つ、プロジェクトローカルのスキルである（たいていは `.cursor/skills/verify-*/`）。候補が複数あれば、どれかを尋ねる。1 つもなければ、対象をでっち上げず、止まって `/create-verification-skill` を案内する。

1. **索引の整理。** 機能マップの README を読み、同じディレクトリのファイルを glob で集める。欠けている、余分な、重複した、リンク切れの項目を直す。軽い作業にとどめ、一覧の生成はしない。

2. **ソースの一斉調査。** 機能ファイルごとに読み取り専用のサブエージェントを 1 つ、並行して起動する。それぞれが「このユーザー向けの機能はどう動くか」をソースから説明し、ドキュメントのずれと思われる箇所を引用付きで指摘し、ライブ検証の簡潔な手順を 1 つ返す。子のサブエージェントは、決してアプリを操作せず、決してファイルを編集しない。返す形: 機能の要約 / ソース上の入口 / ずれと思われる箇所、またはなし / 手順 1 つ。

3. **突き合わせ。** どの機能ファイルにも、返ってきた要約がそろっている。重なる手順をまとめ、アプリの状態の数を実際的な範囲で最小にする。引用されたずれは抜き取りで確かめ、問題なしとされた主張を証明し直さない。最近の変更を見渡して、マップから漏れているユーザー向けの接点を探す。漏れていると判断する前に、具体的なソースのパスを求める。

4. **ライブでの点検。** ソースに問題がなさそうでも必須である。操作はすべてコーディネーターが受け持つ。検証スキル自身の起動の方式に従う。サーバーと UI なら、長く動かし続ける 1 つのインスタンスを順に操作する。寿命の短い CLI なら、操作のたびに新しい分離したセッションを使う（どちらにするかは、このスキルではなく、検証スキルの起動（Launch）の節が決める）。すべての機能を少なくとも一度動かし、どんな失敗が起きても、点検の間ずっと 3 つの不変条件を守る。(1) 最後に想定外の振る舞いをして以降にヘルスチェックしていないインスタンスは、決して操作しない。最初の操作の前に診断し、セッションが単位の場合は新しいセッションごとに診断し、操作が失敗したあとにも診断し直す。診断で失敗が見えない場合（正常なプロセスの上で UI が固まった状態など）は、うまくいくことを期待せず、既知の状態に戻すか起動し直す。(2) それまでに記録した証拠は、どの後片付けのあとも残っている。これは思い込まず、指定された場所で確かめる。(3) 操作が起動したものは、その操作に必要な間を超えて残さない。失敗した試行の残骸は、セッションが固まっていても、終了していても、共有されていても片付ける（共有のインスタンスでは、インスタンスではなく残骸を片付ける）。スキルのずれが原因の診断の失敗は、ずれである。点検を `blocked` とする前に、編集の範囲（Edit scope）の中で直して一度だけやり直す。そのとき再起動するのは、修正で無効になったものだけにする。たどり着けない機能を `verified-unreachable` とするのは、具体的な前提（認証、利用権限、OS、外部の状態）と試した経路を添えられる場合に限る。マップがその前提を書いていなければ、それはずれである。トリアージで直したハーネスは、出す前にライブで操作し直す。最後の停止は、実行の最後の操作（そうした証明のやり直しを含む）のあとに行い、実行より長く残るものがないようにする（証拠は、スキルの定めどおり残す）。

5. **トリアージ。** ユーザーの視点の説明が誤っているか欠けている → ドキュメントのずれなので直す。動いている振る舞いをハーネスが操作できない → ハーネスの不足なので直す。ハーネスの修正も、生成時と同じヘルパーの規則（スクリプトは実行可能にし、呼び出し方をスキルの本文に書く）に従う。アプリの振る舞いが実際に壊れている → 製品の欠陥なので、ユーザーのために記録し、この PR には含めない。

6. **出すか止めるか。** changed なら、証明した修正を 1 つの PR にする。その前に、変更したファイルをすべて読み直す。clean か blocked なら、PR は作らず、結果と網羅の範囲を正直に報告する。

実行の簡潔なメモ（網羅した機能、たどり着けなかった前提、確認したずれ、結果）を一時的な場所に残す。コミットはしない。
